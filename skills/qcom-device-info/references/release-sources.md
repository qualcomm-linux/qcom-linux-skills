# Release identification sources on Qualcomm Linux

QLI 1.x shipped a single `Ver_Info.txt` that named the software and firmware
on a device. **QLI 2.x does not ship that file.** The same information is
still there, spread over four sources that have to be read and correlated.
This document is the parse reference for each one, including the traps that
produce confidently wrong answers.

| Source | Answers | Needs root? |
|---|---|---|
| `/etc/os-release` | distro release, `BUILD_ID` | no |
| `/etc/buildinfo` | every Yocto layer's branch, revision and dirty flag | no |
| `/sys/kernel/debug/qcom_socinfo/` | per-subsystem firmware build strings | **yes**, and debugfs must be mounted |
| `/sys/firmware/efi/efivars/Loader*` | UEFI firmware version, bootloader, booted entry | no |

Because the EFI variables are world-readable, the boot firmware version is
obtainable even when the firmware inventory is not.

## /etc/os-release

Written by OpenEmbedded from `DISTRO_VERSION` plus whatever
`OS_RELEASE_FIELDS` lists. A real qcom-distro sample:

```text
ID=qcom-distro
NAME="Qualcomm Linux Reference Distro"
VERSION="2.99+snapshot-f527b7230fa67429e813b2205bf259498efd7387"
VERSION_ID=2.99-snapshot-f527b7230fa67429e813b2205bf259498efd7387
PRETTY_NAME="Qualcomm Linux Reference Distro 2.99+snapshot-f527b72..."
BUILD_ID="32085063241-1"
```

### BUILD_ID is decodable — use it

meta-qcom sets a deliberately marked local default and lets CI override it:

- `meta-qcom/ci/base.yml` — `OS_RELEASE_FIELDS:append = " BUILD_ID"` and
  `BUILD_ID ?= "local-${DATETIME}"`
- `meta-qcom/.github/workflows/compile.yml` — CI writes
  `BUILD_ID = "${{ github.run_id }}-${{ github.run_attempt }}"`, and the S3
  artifact folder carries the same `<run_id>-<attempt>` name.

| `BUILD_ID` value | Meaning |
|---|---|
| `local-<DATETIME>` | built locally; there is no published artifact to compare against |
| `<digits>-<digits>` | meta-qcom GitHub Actions run — open `https://github.com/qualcomm-linux/meta-qcom/actions/runs/<run_id>` |
| absent | not built from meta-qcom's kas CI config: an official CodeLinaro release zip, or a custom kas setup |

### Trap: the snapshot SHA is oe-core's, not meta-qcom's

`meta-qcom-distro/conf/distro/include/qcom-base.inc` sets

```text
DISTRO_VERSION = "2.99+snapshot-${METADATA_REVISION}"
```

and `METADATA_REVISION` is **openembedded-core's** git revision. In the
sample above, `f527b723…` is the `meta` line in `/etc/buildinfo`, not the
meta-qcom commit. Quoting that SHA as "the meta-qcom commit" is wrong, and
it is the single easiest mistake to make here. Since the two are written by
the same build, a mismatch between them means the metadata sources disagree
and the image should be treated as suspect.

Official prebuilt QLI images are published at
`https://artifacts.codelinaro.org/artifactory/qli-ci/flashable-binaries/meta-qcom/`
as `qli-<release>-<image>.zip` (see the `qcom-yocto-download-prebuilt`
skill); those carry a release version rather than `2.99+snapshot-…`.

## /etc/buildinfo

Generated by the `image-buildinfo` bbclass, which meta-qcom inherits from
`ci/base.yml` and qcom-distro inherits from `qcom-base.inc` — so a
qcom-distro image essentially always has it, and its absence is itself a
finding.

```text
-----------------------
Build Configuration:  |
-----------------------
DISTRO = qcom-distro
DISTRO_VERSION = 2.99+snapshot-f527b7230fa67429e813b2205bf259498efd7387
-----------------------
Layer Revisions:      |
-----------------------
meta-ai           = main:3511d6c9669683fc232211eb72e1549d6db6e660
repo              = master:2c63ba215f7a1118497c5ade2d2040c6aef4bb11 -- modified
meta-qcom-distro  = main:fc472762d0f70662e81e69e63981b544536e2663
meta-selinux      = patched-7351443c6579671bcf048817438f1740ad23eaab:ce1430b93f74e3dbeda0141d5d4dc51a0737f810
meta-virtualization = master:cbaa5b92b046a13585105713166c886cdfd5de33
meta              = patched-d51c6e87a10c7c75a692ca86b71af9a818026ecb:f527b7230fa67429e813b2205bf259498efd7387
```

Per `openembedded-core/meta/lib/oe/buildcfg.py`, each line is
`basename(layer_path) = branch:revision[ -- modified]`.

### Layer names are directory basenames, not layer names

- **`repo` is meta-qcom.** kas-container mounts the meta-qcom checkout at
  `/repo`, so its basename is `repo`. There is normally no line literally
  named `meta-qcom`.
- **`meta` is openembedded-core** (its layer directory is `meta`).
- Other layers are kas-cloned into directories named after the repository,
  so they read naturally.
- The names depend on the build setup, so match on both the basename and
  the real layer name rather than assuming either.

### Flags that change the answer

- **` -- modified`** — that layer's git tree was dirty when the image was
  built. The image cannot be reproduced from git alone; treat every
  conclusion drawn from that layer's revision as approximate.
- **`patched-<sha>`** as the branch — kas applied patches on top of
  `<sha>`. The recorded revision is the patched tree, not an upstream
  branch tip, so it will not exist in the upstream remote.

### Parsing

Split on the **first `" = "`**, never on a fixed column. The class pads
names to 17 characters, but longer names (`meta-virtualization` is 19)
overflow the padding and break column-based parsing.

## /sys/kernel/debug/qcom_socinfo/

Root-only, and only present when debugfs is mounted. The directory mixes
two kinds of entries:

- **subsystem subdirectories** (`boot`, `tz`, `adsp`, `cdsp`, `mpss`,
  `gpdsp`, `hyp`, `wpss`, …), each with `name`, `oem` and `variant`;
- **scalar files** describing the SoC itself (`chip_id`, `chip_family`,
  `pmic_model`, `hardware_platform`, `foundry_id`, `raw_version`, …).

Real, healthy output from a qcs9100-ride-sx:

```text
boot   = 00:BOOT.MXF.1.0.c1-00532-KODIAKLA-1        oem=<build-host-a>  variant=SocLeMansLAA
tz     = 01:TZ.XF.5.29.1-00171.1-KODIAKAAAAANAAZT-1 oem=<build-host-b>  variant=MAKAANAAA
adsp   = 12:DSP.AT.1.0.1-00201-LEMANS-2             oem=<build-host-c>  variant=lemans.adsp.lfQ
cdsp   = 16:DSP.AT.1.0.1-00201-LEMANS-2             variant=lemans.cdsp0.prodQ
cdsp1  = 19:DSP.AT.1.0.1-00201-LEMANS-2             variant=lemans.cdsp1.prodQ
gpdsp  = 20:DSP.AT.1.0.1-00201-LEMANS-2             variant=lemans.gpdsp0.prodQ
gpdsp1 = 21:DSP.AT.1.0.1-00201-LEMANS-2             variant=lemans.gpdsp1.prodQ
```

Reading rules:

- **Strip the leading `NN:`** — it is the subsystem index, not part of the
  build string.
- **Empty `name` files are normal.** About 25 of the ~33 subsystem
  directories are empty on a healthy board, meaning that subsystem is
  absent or not loaded. Skip them; do not report them as missing firmware.
- `oem` is the host that built that firmware, `variant` its build variant.
  The three components above come from three *different* build hosts, which
  is why their branches and codenames differ. (Real `oem` values are the
  firmware vendor's internal build-farm hostnames; they are shown here as
  placeholders.)
- The scalar `build_id` file is **empty** on this platform — it is not the
  image build id. Use `BUILD_ID` from `/etc/os-release` for that.

### Firmware build-string anatomy

```text
BOOT.MXF.1.0.c1-00532-KODIAKLA-1
└┬─┘ └───┬────┘ └─┬─┘ └───┬──┘ │
 │       │        │       │    └── release number
 │       │        │       └─────── platform / variant code
 │       │        └─────────────── build number
 │       └──────────────────────── firmware branch
 └──────────────────────────────── component family
```

`TZ.XF.5.29.1-00171.1-KODIAKAAAAANAAZT-1` parses the same way; the build
number itself may contain a dot.

### Trap: different codenames across families are normal

On this healthy LeMans board, `BOOT` and `TZ` report `KODIAK*` while the
DSPs report `LEMANS`. The boot and TrustZone chain uses a different
internal codename family from the DSP firmware. **Never flag "mixed
platform generations" from that**, or every LeMans board reports a fault.

What *is* worth flagging is a disagreement *within* one family — two
`DSP.AT.*` entries with different build numbers means genuinely mixed
firmware.

## /sys/firmware/efi/efivars/Loader*

Written by systemd-boot. World-readable, so this is the one firmware source
that survives a non-root capture.

```text
LoaderFirmwareInfo    = Qualcomm Technologies, Inc. 24614.1796
LoaderFirmwareType    = UEFI 2.70
LoaderInfo            = systemd-boot 261.2
LoaderImageIdentifier = \EFI\BOOT\BOOTAA64.EFI
LoaderEntrySelected   = linux-qcs9100-ride-sx.efi
LoaderDevicePartUUID  = 8ED446A0-7362-654B-AF31-BEB9AEB8EA07
```

- `LoaderFirmwareInfo` is the **UEFI firmware version** — the best answer
  available when socinfo's `boot` entry cannot be read.
- Each file is a 4-byte attribute prefix followed by a UTF-16LE string:
  `tail -c +5 <file> | iconv -f UTF-16LE -t UTF-8`.
- The `-4a67b082-0a4c-41cf-b6c7-440b29bb8c4f` suffix is systemd's loader
  GUID. Glob it rather than hardcoding it.
- `LoaderSystemToken`, `LoaderFeatures` and `LoaderTpm2ActivePcrBanks` hold
  binary data — skip them, they render as garbage.

## Dead ends

Do not report these as build information:

- **`/etc/version`** contains `20180309123456` on every image. It is a
  reproducible-build constant, not a build date.
- **`/etc/lsb-release`** only mirrors `/etc/os-release`
  (`DISTRIB_ID`/`DISTRIB_RELEASE`/`DISTRIB_DESCRIPTION`).
- **socinfo `build_id`** is empty, as noted above.
